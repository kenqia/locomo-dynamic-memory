# M1 / M2 任务定义与验收依据

更新日期：2026-10-05。职责、三轮迭代和时间计划已由组长确认，详见 `../docs/requirements/team-workflow.md`。本文件保存任务定义，不作为完成状态证明。

Notion 是实时任务状态的唯一准本，维护主责、非作者复核人、期限、进度、阻塞及交付链接。成员可以提出新增任务，由组长决定接受、优先级和阶段归属；任务定义与验收标准变更时同步修订正文。阶段快照注明时间和版本，另存 `process/snapshots/`。

2026-10-06已核实三位成员接受私有仓库邀请并拥有write权限；组长确认三人均能访问和更新Notion。首次会议纪要、五张工具与会议截图、阶段快照及成员总体反馈已整理。最新报告与过程包仍需最终复核，实时进展以Notion为准。

## 执行顺序

1. 按已确认职责推进 M1 正文与 M2 提案，核对课程提交与展示口径。
2. 检查三位成员的仓库和 Notion 访问，10 月 6 日 20:00 举行首次线上例会，保存真实纪要与截图。
3. 将任务按原编号关联到 Notion，明确主责、复核人、期限、阻塞和验收标准。AI 在获授权操作时按需更新，失败由负责人补录。
4. 10 月 7 日优化产物，10 月 8 日收尾复核；10 月 9–10 日处理缓冲、真实过程材料和提交检查。

## Milestone 1：团队工作流程

| 编号 | 任务 | 完成依据 |
| --- | --- | --- |
| W01 | 核对团队信息并向成员说明职责 | 队名为“在阴雨天游泳”、Team ID 为 3；四人组资格由组长确认无问题，正式材料标识一致 |
| W02 | 收集成员能力与投入信息，认领模块和 M1 / M2 具体任务 | 组长确认职责表，成员理解分工；每项材料有主责和非作者复核人；明确谁整理汇报、谁上台、谁提交，不由组长包办 |
| W03 | 邀请另三位成员加入现有私有仓库，检查访问与修改权限 | 三人接受邀请，确认能够按约定参与修改；保持私有；邀请与权限变更先获明确确认 |
| W04 | 确认提交信息、变更复核、合入和交付版本约定 | 文档写明可执行的规则，成员理解并按规则贡献；不把未设置的分支保护或 hooks 写成已配置 |
| W05 | 建立 Notion 项目页和唯一任务表，录入本清单 | 创建与共享范围先获确认；四人可访问；有任务编号、里程碑、主责、复核人、期限、状态和交付链接，不复制第二套实时看板 |
| W06 | 举行真实启动会议，确认微信与每周短会的执行方式 | 留存实际时间、参会、主持和记录人、决定、行动项与合适截图；例会每周二北京时间 20:00，20–30 分钟，记录人按已确认顺序轮换；成员核对纪要 |
| W07 | 在 M1 文档中给出各里程碑路线、三轮迭代与缓冲 | 各阶段有行动项和团队自定时间，三轮迭代；组员复核工作量与依赖；这是本轮编写计划，不是执行后续里程碑 |
| W08 | 清理并复核 Team Workflow 草稿，形成可提交版本 | 保留团队、职责、管理、沟通、版本和计划正文；移除助手说明、过时状态和已解决的待定项；组长确认、黎志丽非作者复核，完成优化及收尾检查 |
| W09 | 收集并打包真实过程材料 | 会议纪要、截图、任务快照和版本记录按确认口径组织；ZIP 可打开，访问范围合适，不含凭据与无关私密信息 |
| W10 | 在内容确认后导出并检查 Team Workflow PDF | 先按 P09 确认独立文件或合并方式及页数口径；检查字体、表格、团队信息和与源稿的一致性；本轮已获授权制作，实际检查结果另行记录 |

## Milestone 2：项目提案与课堂汇报

| 编号 | 任务 | 完成依据 |
| --- | --- | --- |
| P01 | 复核背景信息，明确问题、目标与价值 | 用一个具体状态变化场景说明为什么相关记忆不一定有效；区分课件、教师答复和转述，构造场景不冒充实验 |
| P02 | 确认首版必做功能、不做范围及可逆的小扩展 | 必做覆盖记忆构建、检索、状态判断、证据展示和 JSON；扩展不挤占必做功能，不把课程核心要求本身宣称为创新 |
| P03 | 明确使用者、使用流程和可检查的验收场景 | 描述导入、查看、提问、核查、导出；考虑历史问题、当前问题及证据不足；说明每个场景怎样检查 |
| P04 | 确认可解释的候选路线、模块边界与技术约束 | 核对实际数据样例、课程模型限制和关键参考；明确模块输入输出、未知项及替换办法；不要求本轮实现完整系统或锁定复杂架构 |
| P05 | 确认数据、评测与对照计划 | 明确 4 开发、2 测试的课程要求；列出 F1、Recall@K、状态准确率、Full Text 与 Vector RAG，计算口径待脚本核实；只写计划，不编结果 |
| P06 | 清理并复核 Vision & Scope 及 Feature Roadmap，后续导出 PDF | 移除助手说明和杂乱过程信息，问题、功能、边界、阶段路线及风险相互对应；优化轮与收尾轮经非作者复核；最终 PDF 不超过 5 页，当前暂不导出 |
| P07 | 内容稳定后制作可编辑汇报及汇报 PDF | 以现有十页提纲为起点，讲清问题、范围、方法、验证、分工与路线；不只讲流程；核验参考信息，PDF 不超过 10 页；内容确认后另行制作，本轮未制作 |
| P08 | 试讲、准备答疑并检查提交包 | 按 P09 确认的时长完整试讲，统一成员表述；检查为何选择有效记忆、怎样评测、未实现部分等答疑；核对文件、链接、页数与版本 |
| P09 | 确认实际展示与 M1 / M2 提交口径 | 确认展示轮次、时长、是否有问答；确认文档分开或合并、页数、ZIP 内容、接收渠道及命名，不靠旧课件猜具体安排 |
| P10 | 经最终确认后正式提交材料，并完成课堂展示 | 经团队核对的源稿、PDF 和过程材料齐全；按课程口径提交并保留实际回执，现场按准备内容演讲；正式提交属于外部操作，须先获明确确认 |

Notion 中的认领表建议包含：编号、主责、复核人、预计工作量、依赖、团队自定完成时间、状态、交付链接。任务工作量包括沟通、资料核实、修改、排版和复核，不能按表格行数平均分配。

W08、P06 已有第一轮草稿，不必从空白重写。上传草稿不等于成员认可，后续必须有真实复核和修订。W09 只整理过程证据，P08 核对整个提交包，P10 才执行正式提交，避免三项工作重复认领。

## 首次会议要解决什么

1. 说明已确认的分工、技能链路、每周 10 小时预算和三轮迭代计划，收集实际不可用时段。
2. 检查成员仓库与 Notion 访问，讲清任务新增、领取、阻塞、送审、验收与完成条件。
3. 为 W01–W10、P01–P10 在 Notion 中记录具体主责、非作者复核人、期限和链接。
4. 莫远序主持、黎志丽记录；保存真实决定与行动项，检查纪要和截图的共享范围。

## 本轮不展开的工作

- 不为展示提前搭一个没有记忆与状态逻辑的空界面。
- 不在模型入口未确认前批量付费构建记忆。
- 不为创新直接引入图数据库或复杂 Agent 框架。
- 不用 QA 标准答案充当记忆来源，也不对独立测试集调参。
- 不执行 M3–M5 的完整需求规格、模块实现、正式评测或最终报告；只在 M1 / M2 中规划后续路线。
- 本轮制作已获授权的 M1 Word 与 PDF；M2 演示文件按其内容确认情况另行制作，正式上传与提交仍须明确授权。
