# AI 协作工作方式草稿

状态：讨论稿，2026-10-05。本文是项目级上下文草稿，不复制外部 skills，也不替代 Matt Pocock skills 的原始说明。团队确认前，成员可以提出删改意见。

## 目标

四位成员都可能使用 AI 生成代码或文档。项目采用“先理解，再拆分，再实现，再验证”的工作方式，减少生成内容互相冲突、无法复现或无人负责的问题。

## 文件入口

```text
AGENTS.md                 # 项目入口和少量硬约束，待创建
CONTEXT.md                # 项目术语
docs/specs/               # 稳定规格，是否在 M1/M2 启用待确认
process/tickets/          # ticket 正文，是否在 M1/M2 启用待确认
process/meeting-template.md
```

GitHub 保存正文和历史。Notion 只维护每张 ticket 的负责人、复核人、状态、期限、阻塞和链接。不要在两个地方维护两份 ticket 正文或两套实时状态。

## 工作原则

1. 需求不清时先采访，不让 AI 猜测业务范围。
2. 采访结果形成 spec，spec 再拆成 tickets。
3. ticket 必须能独立交付和验证，依赖关系要显式记录。
4. 作者必须理解并运行自己的交付物，不能只复制 AI 输出。
5. review 由非作者完成。普通改动不需要组长逐行审批，高风险改动需要额外确认。
6. 规格变化若影响接口、验收、边界或依赖，先更新 spec，不暗中降低验收标准。
7. 保存重要决定、验证结果和失败原因，不保存全部 AI 对话。

## 何时并行

只有在依赖已满足或接口已明确、不会同时修改同一核心文件、且每张 ticket 可以独立验证时，才并行处理。不同模块不自动意味着可以并行。如果两个人都在决定同一个 Memory JSON、接口或状态标签，应该先共同确定契约。

## 风险分级

- 文档整理和低风险修订采用轻量采访、验收和 review。
- 公共接口、数据格式、主流程和跨模块改动需要额外复核。
- 核心实现和集成任务按外部 skills 的完整方法执行，具体命令和模板不在本文件重复定义。

## 当前边界

M1/M2 的文档仍是草稿。本文件不要求现在安装、复制或配置外部 skills，不要求现在创建完整 ticket 体系，也不要求立即制作 PDF 或演示文件。首次启动会议后，再根据真实体验决定采用哪些最小配置。
