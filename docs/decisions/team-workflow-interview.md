# Team Workflow 讨论决策记录

状态：讨论记录，2026-10-05。以下内容来自组长与助手的采访，记录“已接受的团队方向”和“尚未确认的事项”。它不是最终 Team Workflow，也不是全组共识证明。正式采用前，四位成员需要在启动会议中审阅并确认。

## 目标

团队选择“舒适优先，同时保证稳定交付”。四个人都可以使用 AI 独立推进，但不能把 AI 输出直接当作交付物。流程应帮助成员先理解问题，再独立实现、验证和复核，不应把每个小动作都变成审批。

## 已接受的工作方式

团队采用 Matt Pocock skills 所体现的工作方法。核心链路是：

```text
需求采访 → spec → tickets 与依赖 → 独立实现 → 自测 → review → 合并 → 阶段复核
```

- 需求不清时先采访，不直接生成代码。
- spec 拆成可以独立交付的 ticket，并标出依赖。
- 依赖已满足、接口已明确且不会同时改同一核心文件的 ticket 才并行。
- 每位成员都能阅读 spec、ticket 和验收标准，解释自己的交付物并完成自测。
- 普通文档或低风险改动由作者自测，指定复核人 review，通过后由作者合并。
- 公共接口、数据格式、主流程和跨模块改动需要组长或集成负责人额外确认。
- spec 若改变接口、验收标准、模块边界或其他 ticket 依赖，先暂停受影响任务，更新 spec 和依赖关系。
- 每个里程碑结束时留下与该阶段目标匹配的可检查结果。

## 工具职责

- GitHub 保存 spec、ticket 正文、代码、文档和版本历史。
- Notion 保存 ticket 的负责人、复核人、状态、期限、阻塞和 GitHub 链接。
- 微信用于日常沟通。
- 影响任务、接口、范围、验收或提交的决定进入会议纪要、spec 或决策记录。

## 沟通与阻塞

- 每周短会采用混合模式。成员先用一句话更新状态，再处理阻塞、依赖、接口变化和共同决定，避免逐条朗读看板。
- 成员在下一次短会前仍没有可验证进展时，应在 Notion 标记阻塞并在微信群说明。
- 阻塞任务先由另一位成员协助；仍无法推进时拆小或重新分配。
- 成员可以申请更换 ticket，但要说明原因、更新 Notion 的主责和复核人，并检查依赖影响。
- 工作量用 `S / M / L` 粗估，计入资料核对、AI 输出理解、调试、自测、review、集成、排版、会议和汇报。里程碑结束时复盘隐形工作和返工。

## 变更权限

以下事项需要全组确认：项目范围、技术栈、公共接口和数据格式、扩展功能取舍、验收标准、里程碑提交版本。

日常优先级和普通 ticket 的负责人调整由组长主持，受影响成员参与。组长不逐项批准所有普通改动，只处理跨模块冲突、公共接口、主流程和高风险变更。

## 课程证据与团队自加规则

课程要求团队有角色、项目管理、沟通、版本控制、过程材料、行动计划、两轮迭代和缓冲。以下是团队自加的执行方式：主责与复核人、Notion 实时状态、GitHub 中的 spec/ticket、S/M/L 粗估、AI 代码自测、阶段复盘和最小项目配置。

这些规则服务于可追溯协作。详细规则保存在本记录和 `docs/ai-workflow.md`，最终 M1 文档只保留课程要求和实际采用的摘要。

### 第三轮已确定事项

来源：组长于 2026-10-05 接受 Q12–Q14 的建议。

- 成员可以持续提出需求、缺陷或优化，由组长决定是否接受、所属里程碑、优先级及是否进入当前迭代。里程碑交付目标固定，ticket 可按实际问题新增、拆分或调整。
- 新需求先采访并形成 spec，再经组长确认拆分后发布 tickets。已有 spec 下的缺陷或遗漏关联原 spec；范围、接口、依赖或验收发生变化时先更新相关定义。
- 每项 ticket 有主责、非作者复核人、期限、验收标准和阻塞依赖。只有依赖满足后才开始，并行任务不得争改同一核心接口。
- 一项 ticket 使用一个短期分支。实现与自测后提交待审版本，再进行 code-review、修复和非作者复核，最后合并并验证。
- 验收标准逐项附证据，由非作者复核后勾选；合并与必要验证完成后才标记完成。取消或延期关闭的 Issue 不算交付完成。
- Notion 采用 AI 辅助按需更新。AI 在授权的任务操作中同步状态和链接，失败或缺少权限时明确报告并由负责人补录。此方式不提供无人值守或实时后台同步。
- Notion 保留任务编号、里程碑、迭代、主责、复核人、期限、状态、阻塞及 Issue/PR 链接，不重复维护 spec、ticket 正文。
