## 第 2 页：为什么相关信息还不够

- 示例：先住城市 A，后来明确搬到城市 B。
- “现在住哪里”与“搬家前住哪里”需要不同证据。
- 仅按相似度检索，可能混用旧状态与新状态。

讲述提示：注明这是构造的解释场景，不是已跑通的实验。问题不是只要多召回几条就能解决。

## 第 3 页：项目目标与范围

- 导入长期对话，构建带时间和来源的结构化记忆。
- 根据问题判断保留、更新或替代关系，选择有效证据。
- 回答可追溯，Web 展示记忆、原文和状态解析，支持 JSON 导出。
- 首版不承诺图数据库、复杂 Agent、图片理解或公众账户系统。

讲述提示：说明必做链路优先，扩展功能不会挤占完整性工作。

## 第 4 页：使用流程

建议用一条流程图展示：导入 → 构建记忆 → 保存复用 → 提问 → 候选检索 → 状态判断 → 回答与证据。

- 记忆可供多次提问复用。
- 查看原始轮次，检查答案依据。
- 不把 QA 标准答案当成记忆内容。

讲述提示：这是目标流程，不是已实现界面。不用虚构界面截图冒充系统演示。

## 第 5 页：候选模块与接口边界

- 记忆模块负责输入处理、结构化记录、来源映射和导出。
- 检索模块返回候选记忆与对应证据轮次。
- 状态模块依据问题和时间条件选择有效证据。
- Web 展示答案、历史证据和选择过程。
- 用共同样例及明确契约支持独立开发，具体技术栈待核实后确定。

讲述提示：说清每块产出什么，不罗列尚未选定的框架。API 平台和准确 model ID 未确认。

## 第 6 页：状态判断的重点

- 相关记忆不一定有效，最新记忆也不一定适用于历史问题。
- 保留旧证据，不因当前状态改变就删除历史。
- 对矛盾或证据不足显示不确定性，不强行选一条。
- 候选扩展：展示未采用记忆的理由，便于错误定位。

讲述提示：动态状态判断是课程核心要求，不直接宣称创新。扩展是否有效需要实验支持。

## 第 7 页：如何验证

- 数据：课程指定 4 段开发、2 段独立测试，划分待确认。
- 指标：回答 F1、证据 Recall@K、动态状态判断准确率。
- 对照：Full Text、Vector RAG；项目方法可增加关闭状态判断的消融。
- 记录配置、证据预算、异常和失败样例；不预报提升比例。

讲述提示：Recall@K 需核对来源映射，状态准确率需核对评价单位，官方脚本取得后落实计算口径。
