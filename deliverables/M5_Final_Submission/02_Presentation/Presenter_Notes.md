**演讲备注**：大家好，我们是第三组"在阴雨天游泳"。我们的项目是一个面向长期对话的动态记忆系统：它把多次会话整理成带来源、带时间的记忆，回答问题时给出可以回查原文的引用。我是组长莫远序，负责核心系统和实验；黎志丽负责 Web Console，卓新烨负责时间与事件的扩展研究，田亦洁负责汇报材料和演示视频。

## P2

- 问题：相关不等于有效
- 长期对话里，难的是判断一句话"现在还算不算数"
- 两句话都和问题高度相关，只有结合时间和关系，才能给出正确答案
- 对话里发生了什么
- 5 月 1 日  "I live in Paris." / 5 月 2 日  "I moved from Paris to Rome." /   / 相似度检索会同时找到这两句话
- 同一个问题，两种时间
- "Alex 现在住在哪？"
- → Rome
- "Alex 5 月 1 日住在哪？"
- → Paris
- 计划 ≠ 已完成
- 否定也要保留
- 矛盾不能擅自消解
- 我们想回答：查询时多一步"有效证据解析"，能否稳定地提高回答质量？代价多大？证据在哪一步丢失？
- 合成示例

**演讲备注**：先看一个例子。Alex 5 月 1 日说住在巴黎，第二天说搬到了罗马。问"他住在哪"，这两句话和问题的语义相似度都很高，普通的相似度检索会把它们一起找出来。只有知道哪句话是什么时候说的、后一句替代了前一句，系统才能回答"现在是罗马"；而问 5 月 1 日时，答案又应该是巴黎。类似的还有计划和完成、否定、前后矛盾。这引出了我们的三个问题。

## P4

- 构建与查询流程
- Hybrid 与 Dynamic 共享检索和历史扩展，只差"解析"这一步
- Dynamic 多调用一次模型，从候选中挑出对这个问题、这个时间有效的记忆
- 构建：按片段保存进度，失败只重试失败片段；任何一步没完成，版本就不发布，旧版本继续可用。 / 查询：BM25 与向量各取 20 → RRF 融合 → 历史扩展（≤ 60 条）→ [解析] → 回答，并记录四阶段 Trace。

**演讲备注**：这是构建和查询的流程。构建按片段进行，任何一步失败都不会覆盖旧版本。查询时，两种策略都先做混合检索，再沿已有关系扩展相关历史。Hybrid 直接把候选交给回答模型；Dynamic 先多调用一次模型，从最多 60 条候选里选出真正有效的记忆，再回答。两种策略唯一的区别就是这一步，后面的实验比较的就是它值不值得。

## P5

- 新信息不覆盖旧信息，每个回答都能回到原文

- 记忆关系

- 两种时间
- 报告时间 ≠ 事件时间 / "现在" = 最后一次会话
- 合成示例

**演讲备注**：这是我们的数据模型。一条记忆只表达一个事实，并指向原始轮次。巴黎和罗马之间是替代关系：当前状态更新为罗马，但巴黎这条历史仍保留，用来回答历史问题。Sam 的两个出生年份是冲突关系，系统保留双方来源而不是挑一个。时间上，我们分开记录"话是什么时候说的"和"事情是什么时候发生的"。

**演讲备注**：开发阶段我们在四段开发对话上做了多轮实验，它们帮助我们发现问题、确定配置，但样本和配置都不同，不能和最终结果放在一起比较。最终结论只来自这次实验：两段开发期间从未看过成绩的对话，共 400 道题，两种策略各跑一次。配置在看答案之前固定，失败的题记 0 分不补跑，结果确认完整后才评分。

## P8

- 核心实验结果
- Dynamic 的 F1 点估计略高但区间跨零；费用和延迟高出数倍
- 0.403 vs 0.409
- 事实类 token F1
- 差 +0.007，95% 区间 [−0.020, +0.034]
- 7.90×
- 估算查询费用
- 按已报 token 用量估算，不是实际账单
- 3.51×
- 单题中位延迟
- 2.37 秒 vs 8.31 秒
- 成功 394 vs 389 / 400；17 次失败中 9 次为供应商余额不足

**演讲备注**：这是核心结果。事实类问题上，Hybrid 的 F1 是 0.403，Dynamic 是 0.409，差值的 95% 区间从负 0.020 到正 0.034，跨过零。所以在这次实验的设定下，我们没有足够证据说明 Dynamic 有稳定的质量优势——这并不等于说它没用。另一方面，Dynamic 按已报用量估算的费用约是 Hybrid 的 7.9 倍，几乎全部来自解析这一步；中位延迟约 3.5 倍。成功率略低，但 17 次失败里有 9 次是账户余额不足，不能都算在方法上。

## P9

- 证据保留与未采用的扩展
- 标注来源主要在解析步骤减少；扩展方向没有显示问答收益
- 107 / 400 题在解析后少了至少一个标注来源 / 2 / 400 题在回答阶段因篇幅限制再丢失 / 这不是 107 次错误删除：标注来源不一定是必需证据，例如问 Tim、来源却在讲 John。哪些排除是错的，还需要人工逐题判断。
- 尝试过但没有采用
- Graph 两跳检索
- 最终证据覆盖不变
- 记忆压缩
- 节省可以忽略
- 自适应路由
- 证据覆盖下降
- 时间软优先
- 没有整体收益
- 时间 / 事件 Sidecar
- 已合入 main：默认关闭的独立离线诊断；真实 QA 收益尚未验证

**演讲备注**：为什么 Dynamic 没有带来收益？我们按阶段统计了标注来源的覆盖。Hybrid 从头到尾基本不变；Dynamic 在解析这一步从 0.68 降到 0.53。逐题看，107 道题在解析后少了至少一个标注来源，只有 2 道题是在回答阶段丢的。但要注意，这不是 107 次错误删除——标注来源不一定是回答必需的，比如有道题问 Tim，来源却在讲 John，排除它可能是对的。右边是此前尝试过的扩展，未显示问答收益；时间 / 事件 Sidecar 后续已合入 main，但只作为默认关闭的独立离线诊断，真实 QA 收益尚未验证。

## P10

- 结论与未来工作
- 默认 Hybrid，Dynamic 显式可选
- 我们的结论
- 系统：从原文到记忆、关系、版本和带引用回答的完整链路，可以在网页中逐层检查 / 质量：区间跨零，没有证明 Dynamic 稳定更好 / 代价：估算费用约 7.9 倍，中位延迟约 3.5 倍 / 证据：减少集中在解析步骤，原因仍待判断
- 值得继续研究的方向
- A · 双时间语义：区分事实发生时间与系统获知时间 / B · 证据充足度检索：按缺失证据补检，而非盲目扩大 Top-K / C · 可证明关系 Graph：检验事件路径是否有来源支持 / D · 更强 Benchmark：补充 LongMemEval、MemoryAgentBench、LOCOMO-CONV
- 一个看起来合理的设计，在独立数据上没有显示稳定收益，同时付出了明显成本。 / 我们把它如实记录下来，并据此做出工程选择。

**演讲备注**：总结一下。工程上，我们交付了从原文到记忆、关系、版本和带引用回答的完整系统，每一步都可以在网页里检查。研究上，Dynamic 没有显示稳定质量优势，同时更贵、更慢，所以我们默认使用 Hybrid，Dynamic 作为可选项保留。未来最值得继续研究的方向包括双时间语义、证据充足度驱动的检索、可证明关系的 Graph Memory，以及更有挑战性的 Benchmark。这些方向都能从现有代码和数据模型出发，先提出清楚的问题，再做公平实验。谢谢大家。
